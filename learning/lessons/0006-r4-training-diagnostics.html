Lesson 0006 · R4

训练不是“loss 降了就结束”

本课把一次参数更新、梯度累积、评估和 checkpoint 组成可恢复的训练闭环，并给出面试中可复述的故障诊断顺序。

硬件标签：RUNNABLE_CPU 已覆盖本课；MPS 只做可选烟测，GPU 性能和多卡结论仍属于后续实验。

1. 一次 update 的顺序

model.train()
optimizer.zero_grad(set_to_none=True)
logits = model(input_ids)
loss_sum, valid_tokens = causal_lm_loss_sum_and_count(logits, labels)
loss_sum.backward()
divide gradients by valid_tokens
clip_grad_norm_(...) → optimizer.step()

PyTorch optimizer 只负责根据已有 gradient 更新参数；Optimizer 文档和 Autograd 文档分别对应这两个边界。

2. 为什么按 valid token 累积

如果不同 micro-batch 含有不同数量的 padding 或 masked prompt，逐批取 mean 再平均会改变目标函数。train_loop.py 先累加每批的 loss sum，最后除以整个 accumulation group 的有效 token 总数；测试会把两批累积与一批拼接进行参数对比。

观察量含义异常时先查
loss有效 token 的平均负对数似然label shift、mask、数据、学习率
grad norm更新前梯度的整体尺度爆炸、空梯度、裁剪阈值
eval loss未更新参数上的 held-out 目标切分泄漏、过拟合、train/eval 状态

3. Checkpoint 不是只有权重

可恢复训练至少要保存模型 state_dict、optimizer state、global step、配置和随机状态。save_checkpoint/load_checkpoint 是小型 reference；PyTorch 的 保存/加载教程和 serialization notes是 API 依据。

测试的强断言是：先训练一步、保存、恢复，再训练下一批，参数应与不间断训练一致。若不一致，优先查 optimizer state、step、随机状态和数据顺序。

5. 诊断顺序

  1. shape / dtype / device；
  2. label shift / ignore mask / 有效 token 数；
  3. 梯度是否存在、是否 finite、是否被裁剪；
  4. optimizer 是否 step、学习率和 weight decay 是否合理；
  5. train/eval 状态、数据切分和重复样本；
  6. 最后才考虑扩大模型或更换架构。

6. 回忆题与交付

  1. 为什么保存 optimizer state 会影响 resume 等价性？
  2. 一个 loss 变 NaN 时，为什么不应先换模型？
  3. gradient accumulation 的分母应该是 micro-batch 数还是 valid token 数？
  4. eval loss 变差而 train loss 继续下降，至少给出两个解释。
  • 保存一次 toy checkpoint，并写出其中的五类字段；
  • 用 3 分钟口述训练故障排查；
